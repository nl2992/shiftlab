## Classification of the diff (`git diff 16313bb 32c5cfd -- src/shiftlab/dive/budgeted_promotion.py`)

Six hunks, all in `_monitor_scout_context_policy` or `run_budgeted_promotion`:

1. Declares `certification_log_e_path: list[float] = []` (new local, additive).
2. Batch branch: `certification_log_e_path = log_e_values.astype(float).tolist()` after `log_e_values` is computed. It copies the array and does not feed back into `certified`, `log_wealth` or `log_e_value`.
3. Sequential branch: `certification_log_e_path.append(log_e_value)`. This is a pure record of an already-computed value.
4. After the loop: computes `certification_crossings` / `certification_event` from the recorded path. The result is used only for the new output field (derived value, no state mutation).
5. Adds two keys to the returned row dict: `promotion_event` (`certification_event if promoted else None`) and `certification_log_e_path`.
6. Typing only: `scenarios: tuple[Any, ...]` annotation and `cast(list[str], manifest["artifacts"]).append(...)`. These are runtime no-ops.

Classification: **not logging/docs/formatting-only in the strict sense** (new output columns were added), but **additive instrumentation only**. No hunk changes inputs, RNG draws, query decisions, betting factors, the e-process, the certification test, stopping, the label budget, or any existing returned value. The new fields exist to expose the certification path to the integrated pipeline (`integrated_pipeline.py` reads `certification_log_e_path` and `promotion_event`).

Consumers: `_run_seed` and the confirmation module (`_run_seed_profile`) only select rows by `alpha_allocation` and copy them into a DataFrame, so the two extra keys appear as extra columns (a list column in the streams frame); existing columns and their meaning are unchanged. No signature of `_run_seed`, `_monitor_scout_context_policy` or `BudgetedPromotionConfig` changed.

Side finding, unrelated to this drift: the confirmation manifest also records `analysis_correction` and a different hash for `budgeted_promotion_context_markov_eventwise_confirmation.py` (pre-correction `6a8047de...`, current `fd217c8a...`). That is a documented paired-contrast mapping fix applied to the saved rows, and was not examined here.

## Limits

- The CUDA path was not re-run, and the saved 600-seed streams were not regenerated. The historical `8eada2f9` run was on cuda; CPU old-vs-new equality says nothing about cuda numerics beyond the source argument that the diff does not touch computation.
- Equivalence is claimed for `budgeted_promotion.py` only, assuming the other source files are as at HEAD (the manifest records other hashes for the confirmation module; this check did not rebuild the exact historical tree).
- The saved confirmation parquet files predate the extra columns, so a rerun at HEAD would differ in schema (two additional columns), not in values.
