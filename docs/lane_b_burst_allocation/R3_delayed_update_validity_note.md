# Validity of release-time e-process updates in harness v2 (lead note, 2026-10-29)

**Status: a lead derivation; it has not been independently reviewed.** It scopes what harness v2's
`DelayedHT` may claim. Lane A records the fixed-delay case: under a fixed, ordered label delay with
predictable querying and a pathwise budget, the event-time Ville argument still holds (Lane A
checkpoint on the e-detector baseline). This note restates that for the v2 implementation and marks
where it stops.

## Setting

- **Fixed at event time `t`.** These are fixed from information available before the coin:
  - propensity `q_t`;
  - bound `B_t = C/q_t + ε`;
  - the stake grid.
- **Coin.** The coin `G_t` is independent of `Z_t` given `F_{t−1}` and `X_t`.
- **Increment.** `V_t = G_t Z_t / q_t − ε` (or `−ε` on agreements).
- **Application time.** Harness v2 applies the factor `1 + λ V_t / B_t` at the release round `r_t`.

## Claim (fixed, deterministic delay)

If `r_t = t + d` for a fixed `d`, then wealth after round `s` is the product of event-time factors
for events `t ≤ s − d`. Apply the event-time supermartingale argument to that product. Its value at
round `s` equals the event-time process stopped at `s − d`, and that index is deterministic. Ville's
inequality therefore applies, so `P(sup_s W_s ≥ 1/α) ≤ α` under the null. In words: delay postpones
alarms but does not inflate the error.

**Needed:** stakes and bounds must not depend on labels released between `t` and `r_t`. In v2 they
are fixed at event time, which satisfies this.

## Out of order and stochastic delays

- **Delays independent of outcomes.** Suppose `r_t` is independent of `{Z_s}` given the past, as with
  OPSD's 1–2 round release driven by the calendar. Then the set of factors applied by round `s` is a
  random subset that is independent of outcomes. Each factor still has conditional mean at most 1
  given its own event-time σ-field. The process indexed by release order is a supermartingale with
  respect to the filtration generated by releases and event-time information. This needs the
  multiplication order not to depend on unreleased outcomes; it can depend only on the release
  schedule.
- **Informative delays.** If release time depends on the outcome, the argument fails.
  **Not covered.**

## Missing labels

- **What v2 does.** It treats a missing label as "unobserved", which sets the HT term to 0.
- **When that is valid.** It is valid only if missingness is independent of `Z_t` given `F_{t−1}`
  and `X_t` (missing completely at random given the public past). The increment is then effectively
  `V_t = G_t M_t Z_t / q_t − ε`, where `M_t` is the observation indicator.
  - Under the null, `E[V_t | F] = P(M=1) E[Z_t] − ε`.
  - If the null holds with `E[Z_t] ≤ ε`, this is at most `ε(P(M=1) − 1) ≤ 0`, so validity holds:
    missing labels can only remove positive evidence. Power is lost.
  - The argument uses `E[Z|M=1] = E[Z]` (missing at random).
- **Informative missingness.** Missingness that depends on `Z` is **not covered**.
- **The data here.** On OPSD the one missing development label is on an agreement round, so the case
  does not arise in development.

## What harness v2 may therefore claim

| Regime | Validity of `DelayedHT` alarms |
|---|---|
| Fixed delay (Binance d=1) | Holds (time-shifted Ville) |
| Calendar-driven delay independent of outcomes (OPSD 1–2 rounds) | Holds (release-order supermartingale) |
| Missing at random given the public past | Holds, with lost power |
| Informative delay or informative missingness | **Not covered** |

Power and delay are separate questions. Nothing here shows the monitors detect anything; the
development smoke had no alarms.
