# WP3 registration and analysis-code chronology (partial W02/W03)

The historical 20-path WP3 stop is supported by an unusually explicit *protocol* chronology. The protocol introduced in `8243711` fixes the four observation policies, engine panel, primary candidate, 75%-onset/5%-budget cell, all-incumbent gate and seven secondary cells. `d0a350a` adds the horizon-SR proof; `e6f428d` records `d0a350a` as the freeze at 2026-10-27 14:30:35 UTC; `dc39f9c` clarifies neutral-skip histories and descriptive bootstrap before run-source commit `7536f11`. Git ancestry places all four commits before that run-source commit. The ignored archived `launch.json` records run start 2026-10-27 14:36:31.720487 UTC at `7536f11`. Its protocol SHA-256, `8f190de7c8439137ec43135e2b73c4a30ce0d9279af1af532ed417c9c098ca8d`, equals the bytes of the protocol at `7536f11`. These observations support protocol-before-recorded-run ordering; Git author/commit times and local launch metadata alone cannot prove the seed block had never been accessed earlier elsewhere.

The same launch record lists `scripts/analyze_data_efficient_prescreen.py` among three **untracked** paths at run start. Its first visible Git commit is `0ec8f6a`, dated 2026-10-27 14:43:34 UTC, approximately seven minutes after the recorded launch. The archived analysis manifest records script SHA-256 `9e1e17d2b1436b458a9fedf075ec49c7c613066115d2308b5abf94e34ef21035`; this matches both the current tracked file and the `0ec8f6a` blob. Thus the preserved analysis is byte-recoverable, but this evidence does **not** establish a Git-frozen analysis implementation before the first path outcomes. No evidence here proves the analysis was changed in response to outcomes either. The protocol itself fixed the point-estimate decision rule and states the bootstrap is descriptive.

The protocol pre-registers a *family*, not the identity of the later best observed arm. The results report selects `optional_temporal/fixed1/started` as the fastest observed 20/20 primary comparator. Selection is compatible with the frozen all-incumbent gate, whose failure does not depend on treating that arm as preselected. The selected-pair interval is descriptive and unadjusted for within-family selection. In the archived raw panel, the candidate fails 48 of 208 eligible primary pair gates, independently reconciled in `WP3_PAIRED_COMPARATOR_AUDIT.json`. The original failure is therefore retained; this chronology gives no basis to promote the result to an independent confirmation or to label the selected pair a registered single-comparator test.

The separate `scripts/retrospective_audit/audit_wp3_source_manifest.py` checks the complete run manifest against the recorded Git tree and ignored original-worktree files. All 181 recorded source hashes reconcile: 165 are exact Git blob hashes, and the remaining 16 match physical CRLF files whose LF normalization equals the corresponding Git blob. All 42 run-output hashes (launch, 40 path files, streams) match. The current original-worktree files match 179/181 recorded physical hashes; `eprocess.py` and `gated_monitor_comparison.py` differ locally after the run, while their run Git blobs still match the recorded hashes. This is source provenance, not an event-level algorithm replay. Full counts and paths are in `WP3_SOURCE_PROVENANCE.json`. The archived `path_*.csv` and `streams.csv` contain one aggregate outcome per arm/engine/detector, including first alarm, resource totals and censored delay. The run's `one_path` writes only these aggregates; it does not preserve the 2,400 event scores, query masks or detector wealth paths. Event-level replay therefore requires regenerating a path with the executed source and seed, not merely rereading the archived CSVs.
