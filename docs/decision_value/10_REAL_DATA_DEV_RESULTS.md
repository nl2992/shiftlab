## 1. Design

**Commands** (two processes; the last `print` of each part crashed on a cp1252 path-encoding error after all outputs and registry entries were written, now fixed; merge/analysis was run afterwards):
```
export PYTHONPATH=$WT/src
python scripts/decision_value/run_real_data.py --data-root <data> --pairs opsd_frozen_vs_sliding opsd_frozen_vs_tso opsd_tso_vs_sliding --run-id replay_20261030T231500Z_partA --run-dir <out>/replay_20261030T231500Z/partA
python scripts/decision_value/run_real_data.py --data-root <data> --pairs monash_frozen_vs_sliding binance_frozen_vs_sliding --run-id ..._partB --run-dir <out>/.../partB
python scripts/decision_value/run_real_data.py --merge <out>/replay_20261030T231500Z <partA> <partB>
```
**Pairs** (incumbent vs challenger): OPSD frozen ridge vs sliding ridge (refit delay 2 d), frozen ridge vs TSO day-ahead forecast, TSO vs sliding ridge; Monash frozen vs sliding (control); Binance frozen vs sliding logit (null control). Loss series are those of phase 1 (`audit_real_data.day_ahead_task`), re-run on a validation window and the dev window.

**Granularity.** OPSD and Monash: **daily** MAE (% of fit-window mean load). The day-ahead forecast is one decision per day, a day's loss is released at once, and hourly steps within a day are strongly dependent and share one decision, so daily gives T = 729 (OPSD) and 275 (Monash) independent-ish decisions without pretending 24x more. Binance: native hourly bars (T = 4,415, 0/1 error, one decision per bar). Delays d in {1, 7} **steps** (days for load, hours for Binance); d = 1 is the minimum operational delay at daily granularity (day D-1 is incomplete when D is forecast). Hold H in {7, 30} steps. Costs c_s in {0,1,5,20} raw loss units (percent-points of mean load per day for load; 0/1 errors for Binance; so c_s = 20 is about 6 OPSD days of loss but 20 Binance bars). c_q = 0 (labels free; q is an information constraint only). q in {0.25, 1}.

**Scaling (train-only).** Validation window: OPSD 2017; Monash 2013-01..03 (90 days, short); Binance has no validation window, so a pseudo-validation was built by shifting the same pair specification back one quarter (frozen on 2025-01..03, evaluated 2025-04..06, 2,183 bars). Scale `s = 1/(4 sd(l0-l1))` on validation, paired step clipped to [-1,1] (dev clipped steps: OPSD 6/18/19 of 729, Monash 19 of 275, Binance 0); incumbent target uses a separate cap `B = 1.25 max(val l0)` (one Monash dev step clipped). Values per pair are in `scaling.json`/`tables.md`. **Costs always use raw losses**; scaling only feeds monitors. Monitor hyper-parameters were declared once, same for all pairs, untuned: CUSUM k = 0.05, PH delta = 0.025, batch n_b = 14, SR and Kelly engine defaults.

**Thresholds.** Declared null: *unconditional stationary null from the validation window*; paired target = moving-block bootstrap (block 7 d; 24 h for Binance) of validation paired differences recentred to mean 0; incumbent target = block bootstrap of validation incumbent losses. alpha = 0.05 for any alarm over the episode horizon, per (monitor, target, d, q, horizon), 2,000 null episodes, separate fresh-seed check (500 episodes): mean null alarm rate per (pair, target, monitor) 0.037-0.062, per-cell maximum 0.074 (target 0.05; n = 500 so s.e. about 0.01). **This is not the conditional excess-cost null**: it is marginal, stationary within validation, inherits the validation block structure, and is not claimed valid under adaptation or non-stationarity (the dev windows are not stationary relative to validation: the whole point).

**Uncertainty modes** (one real series gives no independent replications): `actual` = the realised dev series with 100 independent query masks (q<1; query randomness only; q = 1 is one deterministic episode); `roll` = rolling origins (OPSD H = 365 step 7, 53 episodes; Monash 180/7, 14; Binance 2000/168, 15) with heavy overlap; `bootS`/`bootL` = moving-block bootstrap of joint paired losses, 100 series, block 7/28 d (24/168 h), which captures temporal-sampling variance under within-block dependence but breaks regimes longer than the block (understates persistence and monitor value). **The planned block-bootstrap CI over rolling origins is degenerate** (block length 53 = number of origins, so every resample equals the data); roll results are therefore reported only as spreads, with an effective sample of about T/H = 2.

## 5. Verdict and limitations

- **Value exists but is small and fragile relative to headroom on these streams.** The only large V (OPSD frozen/sliding, +122 to +142 vs never) is "switch once to a challenger that is better throughout", which the best simple reference (always-challenger, or static28) beats by 28 units; the monitor is not adding value over the simplest static policy. The only genuinely dynamic task (TSO/sliding, H_T 466 at cs = 5) yields +24 (5% of headroom) for one CUSUM-Hold7 cell on the actual series and negative or null for everything else; it does not reproduce under bootstrap or d = 7. Using the engine contract's reversal rule (detection advantage and cost disadvantage), TSO/sliding exhibits detection-cost inversion in the actual series and in both bootstraps; this is one series.
- Imposed delays and costs: no real label-release times or application costs; Binance fee (0.1%) was not used. c_s units differ across tasks.
- Single series per pair; variance modes capture only query randomness (`actual`), heavily overlapping origins (`roll`, CI degenerate), or broken persistence (`boot`). No claim of statistical significance for any monitor ranking.
- Exposure: OPSD 2018-19 dev window was already inspected in phase 1 (headroom, loss-difference autocorrelation), the ridge penalty was selected on 2017 in phase 1, challenger design and the monitor HP were fixed before the replay but the choice of pairs and the granularity were made after seeing phase-1 dev headroom. OPSD snapshot may contain revised values (`publisher_checksum_verified` false). The TSO forecast is an external model; the release clock is regulatory, not in the file. Monash validation is only 90 days; Binance pseudo-validation is a shifted replica, not a true validation set; Monash timezone is unspecified.
- Calibration is for a marginal stationary bootstrap null; fresh-seed null alarm rates are 0.04-0.07 (mean), but alarms in dev are driven by non-stationarity by design, and PH is conservative (0.02-0.05).
- Monitor HPs are untuned placeholders on scaled inputs; e-process monitors (SR, Kelly) are mostly silent at these signal-to-noise ratios (sd of scaled step about 0.25), which is itself a result about conversion at T of a few hundred days. Different HPs could change rankings.
- Roll CI bug/design flaw (degenerate block bootstrap) noted above; not re-run to avoid dev-outcome-driven edits.
- Continue/pivot/stop for the real-data leg: **continue only as a small confirmatory sanity check** (OPSD TSO/sliding as the one dynamic pair, Monash/Binance as controls) and **pivot** the headline of the real-data contribution to "behaviour under imposed delay and cost"; stop treating frozen-vs-challenger pairs with a persistently better challenger as monitoring evidence, because always-challenger dominates.

## 6. Proposed FROZEN real-data confirmation protocol (proposal only; not run; to be hashed with this file and the scripts before any reserved window is read)

1. **Windows.** OPSD reserved 2020-01-01..2020-09-30 Europe/Berlin (rows with utc_timestamp >= 2019-12-31T23:00, about 274 days; disclosed forking path: spring-2020 demand disturbance is public); Monash 2014; Binance 2026-01..09 (unopened zips, checksum validation). Opened once each, in one run, no re-run after seeing results; any code fix after opening is reported and the original result retained.
2. **Pairs.** Primary: OPSD TSO vs sliding ridge (incumbent TSO; dynamic regime). Secondary: OPSD frozen vs TSO, OPSD frozen vs sliding (reported but flagged "static-dominated": primary comparator for these is always-challenger, not never). Controls: Monash frozen vs sliding, Binance frozen vs sliding. Model specifications, windows, refit rule (365 d, refit delay 2 d) exactly as phase 1; for OPSD the frozen model is refit-free from the 2015-2016 fit and the ridge penalty is fixed at the phase-1 value.
3. **Monitors/threshold.** Paired target only for the primary: CUSUM (k = 0.05), PH (delta = 0.025), batch (n_b = 14), SR betting, Kelly-H2c-inspired, hyper-parameters as in this file; scaling from the 2017 (OPSD), 2013-Q1 (Monash), pseudo-validation (Binance) windows as fitted here (no refit on dev or reserved data). Thresholds: stationary block-bootstrap null from the same validation windows at alpha = 0.05 over the reserved horizon, per (d, q); recalibrated only for the reserved horizon length. The null is declared marginal, not conditional.
4. **Controller.** Primary: Hold(7); pre-declared secondary: Permanent, Hold(30), Reverse. References: never, always, calendar28, static28; hindsight dynamic oracle on realised losses (never deployable).
5. **Costs/delays/queries.** Primary c_s = 5 loss units (about 1.5 days of mean daily load error; chosen because it is the dev-window value at which headroom is clearly above noise and below the point where only TSO pairs retain headroom), d = 1, q = 1. Sensitivity: c_s in {0, 1, 20}, d = 7, q = 0.25 (100 mask seeds). Labels free.
6. **Primary endpoint.** Difference in net realised cost of the best-declared monitor (the monitor with the lowest validation-window-calibrated threshold-matched null alarm rate is not used for selection; instead the primary monitor is **CUSUM** with Hold(7), fixed here because it produced the only positive actual-series cell and so carries selection risk, disclosed) minus **the better of never and calendar28**, on the OPSD TSO/sliding pair, c_s = 5, d = 1, q = 1. Secondary: V vs never for all 5 monitors x 4 controllers; fraction of hindsight headroom H_T; reversal classification (`statistics.classify_reversal`) of detection ranking vs cost ranking; controls must show V <= 0 for cs > 0.
7. **MME.** 1% of never-switch cost for the primary pair (dev scale: about 24 loss units over 274 reserved days, scaled by length) and the controls' require value <= MME to pass as "no value".
8. **Uncertainty.** Moving-block bootstrap of the reserved-window paired losses (block 7 and 28 d, 10,000 resamples), reported as sensitivity, with the caveat that it understates persistence; query-mask randomness for q < 1 via 100 seeds; Holm correction across the 4 pre-declared secondary comparisons. One real window means no independent replications: state conclusions as case evidence, not population claims.
9. **One-shot rule.** Single execution; results, failures and negative results appended to the research ledger; no change of pairs, monitors, thresholds, c_s, d, q or endpoint after opening; no tuning on reserved data; the OPSD 2020 forking path is disclosed in any report.
10. **Pass/fail.** Evidence of monitoring-to-decision value on the real pair requires the primary endpoint CI (block bootstrap) to exclude zero in favour of the monitor and exceed MME, with both controls at V <= MME; otherwise the real-data leg is reported as a negative or uninformative result.
