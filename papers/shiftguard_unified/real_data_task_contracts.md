# Real-data task contracts for development

**Status:** provisional development contracts, updated 2026-10-26. These contracts use the availability audit in [`real_data_inventory.md`](real_data_inventory.md). None of the existing inspected real-data splits is approved as untouched final confirmation. Each task is a candidate development or descriptive replay until its source-use audit, release clock, and exact feature/split provenance are recorded.

## Cross-task rules

- Keep real-data task results separate from controlled synthetic calibration. A real historical replay does not validate an anytime error guarantee.
- The evaluator may use offline outcomes to score methods after the replay. The learner may only use information available at its declared decision time.
- For each task, state which event/availability times are verified, assumed or unknown. Unknown label-release times prohibit claims of prospective online deployment.
- Cost matrices used without application elicitation are **imposed research costs**. Report official task metrics separately from cost-sensitive results and include a cost sensitivity curve rather than selecting the most favorable ratio.
- Group/domain/time splits do not automatically provide independent replications. Bootstrap at the independent unit (entity, domain, or temporal block), not at the row level.
- Until prior test use is audited, all observed test segments are development/descriptive data. A final confirmation task needs a new, pre-registered holdout or a new external period with a verified release clock.

## Project GATE public-use randomized intervention candidate

The public-use files are locally acquired, hash-verified and parsed. DOL's final evaluation explains that 4,198 applicants were randomized and one nonrandomly assigned applicant was removed, yielding the public 4,197-record analysis file. The report further removes 120 members of mixed-treatment business partnerships to prevent spillover; the public-use schema supplies neither partnership IDs nor individual analysis weights, so this published analysis population cannot be reconstructed exactly. The report states a 50/50 assignment probability and assignment less than a week after application on average; eligible application fields are baseline covariates. The supplied wave files contain 3,449/3,038/2,450 records and uniquely link to application `gateid`s. Follow-up response falls from 80.4%/84.0% (control/offer) in wave 1 to 55.9%/60.8% in wave 3, with response higher in the offer arm. A complete-case policy value is responder-conditional; a population effect needs a justified response model and sensitivity analysis.

Candidate fixed-horizon contract: wave-3 `dwkc_a` is a binary endpoint for current self-employment at respondent interview. It is observed for 2,450 people (58.4% of the 4,197-file cohort); control/offer response is 55.9%/60.8%. Interview timing is 1,375–2,101 days after assignment (median 1,706), and label-release times are unknown. Assumption-free missing-outcome bounds span −42.0 to +41.2 percentage points; they omit sampling uncertainty and the mixed-arm partnership exclusion/interference issue. DOL reports a $1,321 invoice-based program-group cost, but its dollar year and applicability to individualized offers must be verified. Use application-only pre-assignment features; train/select policies on development data; and evaluate once on disjoint participants using the 0.5 randomization probability. Before fitting, define a response model and sensitivity analysis and decide how to handle the unobserved mixed-arm partnerships; the public files cannot reproduce DOL's 4,078-person analysis sample. Keep complete-case findings responder-conditional, separate the binary endpoint from any monetary outcome, and do not claim net dollars until units and cost timing are aligned. Treat results as fixed-horizon RCT policy evaluation, never sequential monitoring. Provenance and open constraints are in `project_gate_data_candidate_audit.md` and `project_gate_source_audit.json`.

## Provisional development design

**WILDS PACE update (2026-10-26):** one offline, article-separated fixed
candidate comparison now evaluates the PACE paper's binary-correctness gate
against fixed-N exact McNemar. PACE retained the incumbent while fixed-N
promoted the selected candidate. This is exploratory and does not alter the
WILDS eligibility decision: no verified chronology, no application costs,
prior test exposure, and no active label acquisition or causal intervention
contract. See `wilds_pace_gate_protocol_v1.md` and the matching output folder.

The first real-data development pass should be a **two-panel evaluation**, not one pooled leaderboard:

1. **Offline common-label policy panel:** WILDS CivilComments now has one exploratory sample-split threshold/model-selection evaluation. Add the required Gas Sensor batch-domain study (or Folktables if its task/exposure audit is cleaner). Train candidate classifiers without test outcomes, score fixed policy pairs from observed test labels, and report distribution discrepancy, predictive risk and paired decision cost separately. Costs remain declared sensitivity controls. Use article/domain-level uncertainty and do not call domains a continuous stream.
2. **Chronological/delayed panel:** CRSP and Criteo Attribution, with CRSP restricted to descriptive historical return replay and Criteo using a maturity clock clearly labeled as assumed. Evaluate predictive-risk and label-budget behavior; only compare downstream policy costs if the action/outcome observability contract is satisfied. Report no prospective statistical guarantee for these replays.

OBD supplies a full-archive real-data Q2 policy-value development task. Criteo BLBF is a second potential logged-bandit source with recorded banner propensities, but only its small nonchronological sample is available locally; its source also outcome-subsamples non-click impressions. No current source supports matched Q1–Q3 evaluation with verified outcome-release clocks and operational costs. Keep both logged-bandit sources offline until their action, correction, support, feature-timing, and feedback contracts are established. The OBD BTS count discrepancy remains open, and the BLBF full archive requires storage outside the current C: volume.

## Eligibility gate before any real benchmark run

A dataset/task can enter a registered development comparison only after its task contract records:

1. exact source/version/hash and selected task columns;
2. feature, event, decision, label request, label availability and maturity clocks, including explicit `unknown` entries;
3. train/development/calibration/confirmation assignment and a prior-use audit;
4. learner-visible versus evaluator-only fields and tests that prevent leakage;
5. candidate policies, reference policy and whether actions affect outcomes;
6. the primary estimand and any imposed costs with predeclared sensitivity values;
7. the independent uncertainty unit and analysis plan;
8. applicable baselines and feedback compatibility;
9. resource budget, stopping condition, outputs and manifest schema.

If any field cannot be established, run only the narrower task it supports and label the result accordingly. A dataset's presence in `data/processed` alone does not pass this gate.
